# Архитектура: границы модулей

Правила для проекта, созданного из шаблона. Дополняют раздел Anti-Monolith в
[AGENTS.md](../AGENTS.md): там про размер и связность файла, здесь - про
направление зависимостей между модулями.

## Слои и направление зависимостей

| Слой           | Что содержит                              | Может зависеть от             |
| -------------- | ----------------------------------------- | ----------------------------- |
| UI             | компоненты, страницы, стили               | сценариев, домена, общих      |
| Сценарии       | варианты использования, оркестрация       | домена, адаптеров             |
| Домен          | правила предметной области, типы, расчёты | ничего из перечисленного      |
| Адаптеры       | HTTP-клиенты, хранилище, внешние сервисы  | домена, общих утилит          |
| Общие утилиты  | форматирование, конфиг, типы-примитивы    | только стандартной библиотеки |
| Инфраструктура | сборка, тесты, скрипты                    | любого слоя                   |

Зависимости направлены внутрь: `UI -> сценарии -> домен`. Обратное направление -
сигнал ошибки границы, а не повод для исключения.

## Жёсткие правила

- UI не импортирует внутренности слоя данных: только через сценарий или адаптер.
- Домен не зависит от React, HTTP, базы и конкретного клиента. Проверяется
  ревью: типы домена не должны упоминать `Response`, `Request`, ORM-модели.
- Циклические импорты между модулями запрещены. Массовые `index.ts` с
  реэкспортами делают циклы менее заметными - держите публичную поверхность
  модуля маленькой и явной.
- Абстракция не создаётся из-за похожих строк: два похожих фрагмента могут
  выражать разные бизнес-правила.

## Как делить файл

Жёсткий предел - 250 строк для TS/JS, его проверяет `check:file-length`.
Остальные пороги - сигналы для ревью, а не запреты. Пять вопросов перед
разделением:

1. Можно ли описать назначение файла одним предложением без нескольких «и»?
2. Меняются ли его части по разным причинам?
3. Можно ли протестировать главную логику без интерфейса, сети и базы?
4. Нужно ли читать весь файл, чтобы безопасно изменить одну функцию?
5. После разделения станет проще понимать код или появятся только переходы
   между файлами?

## Что проверяется автоматически

| Проверка                    | Инструмент                     | Канал           |
| --------------------------- | ------------------------------ | --------------- |
| Размер файла (250 строк)    | `scripts/check-file-length.ts` | pre-commit + CI |
| Длина функций, сложность 15 | `eslint.metrics.config.js`     | advisory        |
| Типы и импорты              | `tsc --noEmit`, ESLint         | pre-push + CI   |

Границы слоёв автоматически пока не проверяются: правило живёт на ревью. Если
проект вырастет, кандидат - `eslint-plugin-boundaries` или собственное правило
на запрещённые пары импортов.
