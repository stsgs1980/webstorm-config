## 2. Как устроены настройки: проектное против глобального

### 2.1. Три контура настроек

В проекте действуют три контура настроек, и смешивать их нельзя. Первый
контур - **репозиторий**: каталог `.idea/` (закрыт корневым `.gitignore`
и открыт белым списком строк с `!`), конфигурации линтеров в корне,
`package.json` и скрипты. Всё, что коммитится, работает у всех после
клона и является источником истины. Второй контур - **глобальные
настройки IDE** в каталоге пользователя (`%APPDATA%\JetBrains\WebStorm2026.2`
для Windows): тема, кеймап, плагины и всё, что импортировано вручную.
Третий контур - **личные настройки** в `workspace.xml`, который
намеренно не коммитится: File Watchers, React Buddy toolbox, анализ
кода при коммите.

Ключевое правило разделения из аудита: **обязательное для всех живёт
в CI или в скрипте; удобное живёт в глобальных настройках WebStorm**.
Настройка IDE не является проверкой - правило, существующее только в
профиле инспекций, действует на одного человека на одной машине. Отсюда
порядок правок: сначала репозиторий, затем импорт в IDE (раздел 2.4).

защищает от утечки личных настроек, но новый общий файл нужно явно
добавить в белый список.

### 2.3. Живые шаблоны: ловушка IDEABKL-5033 и статус импорта

Живые шаблоны - единственная категория настроек, которая из клона не
работает. Каталог `.idea/liveTemplates/` IDE не читает в принципе
(ограничение платформы IntelliJ, тикет IDEABKL-5033): файлы в
репозитории - «склад», а не рабочие шаблоны. Чтобы шаблоны заработали,
их импортируют вручную через «Настройки -> Редактор -> Живые шаблоны»
(копирование XML через буфер обмена); после импорта они попадают в
глобальные настройки IDE и доступны во всех проектах машины. Контекст
(TypeScript, TSX, JavaScript) включается на группе кнопкой Change после
импорта. Альтернатива - плагин Live Template Sharing (id 25007), который
читает `.idea/liveTemplates/` сам, но тоже кладёт шаблоны в
глобальные настройки.

Статус на 24.10.2026: импорт выполнен в обход UI - четыре XML
(`React.xml` - 8 шаблонов, `Testing.xml` - 4, `TypeScript.xml` - 3,
`Utilities.xml` - 3) записаны напрямую в
`%APPDATA%\JetBrains\WebStorm2026.2\templates\` с прописанными контекстами
TypeScript/TSX/JavaScript; после полного перезапуска IDE все четыре группы
видны в настройках.

При импорте вскрылся дефект шаблона `rafce`: тело вставлялось с
неопределённой переменной `$NAME$`, а неопределённая переменная
расширяется в пустоту - получалось `const  = ...` с последующими
ошибками ESLint и TypeScript. Верификация маркерами источников
показала, что ни проектная, ни глобальная копия не были
исполняемыми. Решение в глобальной копии: переменной `NAME` задано
выражение `capitalize(fileNameWithoutExtension())` с
`defaultValue="Component"` - имя компонента вычисляется из имени файла
автоматически (`test.tsx` -> `Test`) без поля ввода и подставляется во
все четыре места. Дополнительно исправлено тело: добавлен возвращаемый
тип `: ReactElement` (правило `explicit-function-return-type`) и
`ReactElement` в импорт типов. React Buddy в дефекте не виноват - плагин
можно включать обратно.

**Направление правок - правило:** правим в репозитории, затем
реимпортируем в IDE - не наоборот. Обратное направление уже один раз
привело к расхождению: глобальная копия `rafce` исправлена 24.10.2026,
репозиторная оставалась сломанной до 29.10.2026, когда её значения
перенесены из глобальной копии 1-в-1 (глава 5, действие 1). Глобальное и
проектное не конфликтуют: если проект несёт свою схему или профиль,
проектная версия выигрывает - и они согласованы с проектом.

### 3.1. Почему шаги 2-5 важны

Шаги 2-5 переводят настройки из категории «существуют только в этом
проекте» в категорию «доступны в любом проекте». Шаблоны файлов в
проектном скоупе работают только там, где есть свой `.idea/fileTemplates/`;
перенос в IDE-скоуп делает их доступными во всех проектах машины.
Глобальная схема Code Style и профиль инспекций служат мягкой базой:
в проектах со своими схемами проектная версия выигрывает, в остальных
действует глобальная. Дефолты для новых проектов закрывают самый частый
источник рассинхрона - каждый новый репозиторий сразу стартует с
Prettier и ESLint на сохранении, без ручной настройки.

## 4. Ложные срабатывания IDE: каталог и обходы

### 4.1. IJPL-101766: «Unknown character category»

**Симптом.** Строка с валидным ES2018-паттерном
`/\\p{Extended_Pictographic}|\\p{Regional_Indicator}/u` в `eslint-rules/unicode-policy.js`
подсвечивается как «Неизвестная категория символов», хотя Node, ESLint и
`tsc` файл принимают.

Подсветка подтверждена вручную 24.10.2026 в WebStorm 2026.2.3. Это ложное
срабатывание валидатора IDE, а не ошибка правил: свойства валидны в ES2018
и работают в рантайме.

На рантайм, ESLint, `tsc`, тесты и CI проблема не влияет - она существует
только в UI редактора.

**Первопричина** (воспроизведена по исходникам платформы). `RegExpAnnotator.visitRegExpProperty`
проверяет каждое `\\p{Name}`.

`RegExpLanguageHost.isValidCategory`. `DefaultRegExpPropertiesProvider` знает
только PCRE/Java-категории (`L`, `Lu`, `So`, `Cn`…) и POSIX-классы
(`alnum`, `space`…).

Бинарных свойств TC39 (`Extended_Pictographic`, `Emoji`, `Regional_Indicator`)
в `DefaultRegExpPropertiesProvider` нет.

Иными словами, IDE валидирует JavaScript-регулярку по списку PCRE, а не по
таблицам Unicode движка.

Это дефект платформы: тикет IJPL-101766 (бывший IDEA-269827), статус Open,
исполнитель Bas Leijdekkers, приоритет Normal; дубли - IJPL-101771 (про
`\\p{Emoji}`) и связанный WEB-27639. Исправления нет.

**Почему `// noinspection Annotator` не гарантирует подавление.** В файле уже
стоит `// noinspection Annotator` - документированный способ отключить
группу Annotator. Но отдельного ID у RegExp-валидации не существует
(инспекции `JSUnicodeRegexp` нет), а по данным IDEA-133895 инспекция группы
Annotator доступна только в batch-режиме: в отчёте инспекций подавление
может сработать, в редакторе - нет. Полагаться на него нельзя.

**Таблица 4.1 - обходы по убыванию надёжности:**

| Способ                                      | Надёжность  | Цена                                              |
| ------------------------------------------- | ----------- | ------------------------------------------------- |
| Рантайм-сборка: `new RegExp` + `String.raw` | Высокая     | IDE не подсвечивает собранный паттерн             |
| Явные диапазоны кодовых точек               | Высокая     | 156 диапазонов, 2848 точек, паттерн 2512 символов |
| `// noinspection Annotator`                 | Низкая      | В редакторе не гарантирует подавление             |
| `//language=RegExp` перед литералом         | Нет эффекта | Управляет injection-ассистом                      |
| Задокументировать false positive            | Высокая     | Требует дисциплины, подсветка остаётся            |

**Текущее состояние:** в репозитории выбран вариант 1а - паттерны в
`unicode-policy.js` собираются в рантайме (`String.raw` + `join`).
Практическое правило: **не сворачивать конкатенацию в литерал** - вместе
с подсветкой вернётся и «дублирующая ветвь» в `new RegExp` с
подстановками. При проверке новых версий WebStorm (приложение Б, пункт
1): ориентир такой: если подсветки больше нет, обход можно свернуть в
литерал.

Вариант 1а - рантайм-сборка (ESLint чист, глифы классифицируются
верно):

```js
const propertyEscape = (name) => String.raw`\p{${name}}`;

const emojiPattern = new RegExp(
  `${propertyEscape("Extended_Pictographic")}|${propertyEscape("Regional_Indicator")}|\\u20E3`,
  "u",
);

// Так паттерн потребляется правилом в eslint-rules/unicode-policy.js
// (строка `pattern: emojiPattern`); демо на кодовой точке без самого глифа:
emojiPattern.test(String.fromCodePoint(0x20e3)); // true - кеймап ловится
emojiPattern.test("a"); // false - буква проходит
```

`String.raw` сохраняет обратную косую черту, поэтому в шаблон попадает
`\p{...}`. В обычной шаблонной строке нужно писать `\\p{...}`; для `\u{...}` -
`String.raw` с одним слэшем либо `\\u{...}`. Слитый `\u20E3` заодно
закрывает keycaps. Минус варианта: IDE не помогает с подсветкой такого
паттерна.

Для справки, вариант 1б: явные диапазоны дают 156 диапазонов и 2848
кодовых точек (0 расхождений с `\p{Extended_Pictographic}` на 0..U+10FFFF,
суррогаты исключены); для `Regional_Indicator` - `[\u{1F1E6}-\u{1F1FF}]`,
для keycaps - `\u20E3`. Паттерн генерируется скриптом, хранится отдельным
модулем, в тестах закрепляется parity-проверка с `\p{...}`.

   лучше четырёх файлов по 75 с искусственными границами.
2. **Не переносить жёсткие пороги в глобальные настройки.** Лимиты
   250/200/50 и `unicode-policy` в другом проекте ложны: длинный DSL,
   сгенерированный клиент, маркетинговые тексты с эмодзи.
3. **Не править шаблон только в `%APPDATA%`.** Именно так репозиторный
   `rafce` остался сломанным при исправленной глобальной копии.
4. **Не считать `// noinspection` решением ложного срабатывания.** В
   редакторе он не подавляет группу Annotator - работает только в
   batch-отчёте.
5. **Не надеяться на Analyze code вместо CI.** Он не запускается в
   пайплайне и не виден AI-агенту.
6. **Не включать Save Actions вместе с нативными «Действиями при
   сохранении».** Гарантированное двойное форматирование и дифф-шум.
7. **Не запускать `npm audit fix`.** Он ведёт на мажорный даунгрейд
   `stylelint-config-standard@15.0.1`; prod-аудит чистый, риск `braces` -
   dev-only и принят (GHSA-vfj7-8cjw-p6xm, фикса нет).

### 5.4. План внедрения

**Шаг 1 - один коммит, полдня:** действия 1-4 из раздела 5.1. Критерий
приёмки: рендер `rafce` проходит `eslint --max-warnings=0` и
`tsc --noEmit`; тесты исключений падают на старой версии скрипта и
проходят на новой.

**Шаг 2 - инфраструктура, день:** пункты 5-9 таблицы 5.1 (судьба `warn`
и `lint:metrics`, type-aware слой, `check-templates.ts`, prod-аудит в
CI, таблица «где проверяется» в docs). Критерий: в таблице нет строки
«обязательное, но не проверяется нигде», CI зелёный.

**Шаг 3 - политика, по мере роста проектов:** `docs/architecture.md`,
`docs/api.md`, `docs/security.md`, E2E на критическом пути, правила
границ модулей. Критерий: у каждого правила есть файл, где оно
закреплено, и способ проверки - автоматический либо явно ручной.

### 5.5. Итоговое решение по порогам

Менять значения не нужно - нужно назвать статус каждого порога
(аудит §4):

| Объект              | Сейчас                    | Решение                             | Где проверяется     |
| ------------------- | ------------------------- | ----------------------------------- | ------------------- |
| TS/JS-файл          | 250 строк, блокирует      | Блокирует, плюс исключения          | pre-commit + CI     |
| React-компонент     | 200 строк, «обязательно»  | Сигнал анализа ответственности      | ревью или агент     |
| Функция             | 50 строк, только IDE      | 50 как сигнал, advisory-отчёт       | IDE + отчёт         |
| Сложность           | 15, только IDE            | 15 - порог; 10 - ориентир           | IDE + отчёт         |
| Параметры           | 5, только IDE             | 4 - повод проверить контракт        | IDE + `max-params`  |
| Вложенность блоков  | не проверяется            | `max-depth` 3 как совет             | advisory-отчёт      |
| Вложенность функций | `NestedFunctionDepthJS` 4 | Оставить как есть                   | IDE                 |
| useState            | 3+ -> hook обязателен     | Убрать числовой лимит               | не автоматизируется |
| Promises            | ERROR только в IDE        | `no-floating-promises`, type-aware  | CI                  |
| Markdown            | 120, aligned tables       | Оставить; emoji - отдельной записью | markdownlint + шаг  |

Два уточнения, из-за которых эти числа часто спорят зря. Первое:
`NestedFunctionDepthJS` (порог 4) - это вложенность **функций**, а не
глубина `if`/`for`/`switch`; ориентир «до 3 уровней» относится к
управляющим конструкциям, и для него нужен отдельный `max-depth` - одно
выдавать за другое нельзя. Второе: сложность 15 в React шумит - тернарник
вида `a ? clsA : clsB` добавляет единицу без реальной сложности; менять
число из-за этого не нужно, достаточно статуса «сигнал», а не
«блокирует».

Отдельно про 250 и JSDoc: лимит считает физические строки, включая
комментарии, а JSDoc обязателен для публичного API (`publicOnly: true`) -
чем лучше документирован публичный код, тем ближе файл к FAIL. Это
аргумент за исключения и статус «сигнал» у порогов, а не за повышение
лимита.

## 6. Стандарты кода: пороги, React, архитектура, надёжность

Справочник для ежедневной работы и ревью. Числа из стороннего обзора
(«файл до 300 строк, функция до 40-60») были эвристиками, а не аудитом
шаблона; итоговое сравнение не рекомендует массово повышать действующие
лимиты.

### 6.1. Размеры файлов, функций и компонентов

**Таблица 6.1 - исходный код и стили** (общее число строк, включая
комментарии и пустые; превышение - повод для проверки, не приказ):

| Тип                          | Диапазон  | Когда проверять | Что проверять                                   |
| ---------------------------- | --------- | --------------- | ----------------------------------------------- |
| `.tsx`                       | 80–250    | >300–400        | Не смешаны ли страница, запросы, формы, правила |
| `.ts`, `.js`, `.mjs`, `.cjs` | 50–300    | >400–500        | Нет ли нескольких независимых обязанностей      |
| `.css`                       | 50–300    | >400–500        | Разделение по компонентам, слоям, токенам       |
| `.html`, `.astro`            | 80–300    | >400            | Выделимость шаблонов и повторяющихся секций     |
| `.py`                        | 100–400   | >500            | Границы предметных задач                        |
| `.sh`                        | 20–150    | >200            | Не стал ли скрипт приложением без тестов        |
| `.sql`                       | по задаче | >300 (ручной)   | Сложность запроса, план, границы миграции       |
| `.prisma`                    | 100–500   | >500–800        | Связность моделей и предметных областей         |

Исключения из лимитов: таблицы констант, декларации типов, тестовые
наборы, миграции и сгенерированный код могут быть значительно длиннее.
Для документации ориентир другой: 100-400 строк на тему и один основной
вопрос на документ; `README.md` - желательно 100-250 строк с быстрым
стартом без чтения остальной документации. Конфигам и данным лимит
строк почти не нужен: для `.csv`, `.lock`, `.map` и бинарных файлов
контролируются размер, схема и валидация, а не количество строк;
`.env.example` содержит имена переменных, но не реальные токены.

**Таблица 6.2 - функции и React-компоненты:**

| Объект                            | Ориентир       | Повод проверить                                       |
| --------------------------------- | -------------- | ----------------------------------------------------- |
| Функция: длина                    | 10–40 строк    | >60–80                                                |
| Функция: параметры                | 0–3            | >4 — проверять контракт; булев флаг скрывает сценарий |
| Функция: вложенность              | до 2–3 уровней | 4+ уровня                                             |
| Функция: сложность                | до 10          | >10–15 — рефакторинг или исключение                   |
| Компонент: небольшой UI           | 30–120 строк   | —                                                     |
| Компонент: с локальным поведением | 80–250 строк   | —                                                     |
| Компонент: страница-композиция    | 100–300 строк  | —                                                     |
| Компонент: любой                  | —              | >300–400 — архитектурная проверка                     |

Компонент пора разделять, когда он: одновременно загружает данные,
вычисляет бизнес-правила и рисует сложный интерфейс; содержит
несколько независимо меняющихся секций; управляет несвязанными
сценариями; имеет вложенные ветвления JSX, которые трудно прочитать;
требует множества несвязанных props; тестируется только с поднятием
почти всего приложения. Большая форма или таблица может обоснованно
превышать ориентиры - критерий связность, а не счётчик.

### 6.2. Обоснованное и перегнутое в требованиях шаблона

Сторонняя оценка требований дала примерно 60% обоснованных правил и
40% перегибов. Оценка - вход для решений главы 5, а не действующий
стандарт: часть перегибов уже устранена или переведена в статус «сигнал».

| Правило                            | Оценка                   | Комментарий                                      |
| ---------------------------------- | ------------------------ | ------------------------------------------------ |
| TypeScript strict mode             | Обосновано               | `noImplicitAny`, `strictNullChecks` ловят баги   |
| jsx-a11y                           | Обосновано               | Требование закона (ADA, EAA), ловит дефекты      |
| `.editorconfig` + `.gitattributes` | Обосновано               | LF/CRLF — реальная боль смешанных команд         |
| Conventional Commits               | Обосновано в связке      | Нужно для changelog; сам по себе — косметика     |
| JSDoc для публичного API           | Обосновано               | `publicOnly: true`; внутреннему хватает TS       |
| explicit-function-return-type      | Перегиб                  | TS выводит 95% типов; error на всё — Java-подход |
| Emoji-запрет (unicode-policy)      | Перегиб для кода в целом | Терминалы устарели; здесь — политика проекта     |
| Хард-лимит 250 без исключений      | Перегиб механики         | Блокирующий лимит + исключения (действие 4)      |
| 3+ useState -> hook                | Перегиб                  | Убирается в пользу смыслового (действие 3)       |

| `check-docs.ts`                    | Ок для шаблона           | Проверка скриптов и путей — лицу шаблона         |

### 6.3. React: состояние и эффекты

- Не хранить вычисляемые значения в состоянии: `fullName` из
  `firstName` и `lastName` считается при рендере, а не синхронизируется
  эффектом.
- `useEffect` - для синхронизации с внешней системой, а не для расчётов
  (они при рендере) и не для реакции на события (они в обработчиках).
- Количество `useState` - не диагноз: десять связанных полей формы
  нормальны, четыре независимые группы состояния уже сигнал смешения
  обязанностей.
- Custom hook должен представлять связное поведение с ясным контрактом:
  вынос 250 строк в `usePageEverything()` не устраняет монолит. Для
  сложных взаимосвязанных переходов - `useReducer`.
- Не определять обычные дочерние компоненты внутри тела родителя: новый
  тип компонента на каждом рендере сбрасывает состояние дочернего
  дерева.
- `memo`, `useMemo`, `useCallback` - при измеренной проблеме, не по
  умолчанию.
- Состояние размещать у ближайшего общего владельца; глобальное
  хранилище - только по обоснованию.

### 6.4. Модули и архитектура

Связность важнее размера: файл на 450 строк с одной обязанностью
лучше пяти файлов по 90 строк с циклическими зависимостями. Делить
нужно по причинам изменения: изменились правила цены - модуль расчёта;
изменился API - адаптер; изменился вид карточки - компонент карточки.

Зависимости имеют направление: UI -> прикладные сценарии -> предметная
логика; предметная логика по возможности не зависит от React, HTTP и
конкретного клиента БД. Публичный интерфейс модуля держится маленьким -
чем больше доступно снаружи, тем сложнее менять реализацию. Циклические
импорты между предметными модулями - сигнал проблемы границ;
массовые `index.ts` с реэкспортами делают такие зависимости менее
заметными. Абстракция не создаётся только из-за похожих строк: два
внешне похожих фрагмента могут реализовывать разные бизнес-правила, и
преждевременный общий компонент с десятком флагов хуже небольшого
дублирования.

Пять вопросов перед разделением файла:

1. Можно ли описать его назначение одним предложением без нескольких
   независимых «и»?
2. Меняются ли его части по разным причинам?
3. Можно ли протестировать главную логику без интерфейса, сети и базы?
4. Нужно ли читать весь файл, чтобы безопасно изменить одну функцию?
5. После разделения станет проще понимать код или появятся только
   переходы между файлами?

### 6.5. Надёжность и безопасность

| Область         | Базовое правило                                                                       |
| --------------- | ------------------------------------------------------------------------------------- |
| Внешние данные  | Проверять на границах: API, формы, файлы, окружение; TS не заменяет runtime-валидацию |
| Ошибки          | Не подавлять пустым `catch`; обрабатывать или передавать выше с контекстом            |
| Сетевые запросы | Таймауты и отмена; повторять только безопасные операции или идемпотентные             |
| Деньги          | Явная стратегия точности; не полагаться на дробную арифметику `number`                |
| Даты            | Явный часовой пояс; различать дату, локальное время и момент времени                  |
| Авторизация     | Проверять на сервере; скрытая кнопка интерфейса защитой не является                   |
| Логи            | Не записывать пароли, токены и лишние персональные данные                             |
| База данных     | Транзакции, ограничения, индексы, N+1 и пагинация                                     |
| Доступность UI  | Семантика, клавиатура, подписи полей, видимый фокус                                   |
| Тестирование    | Проверять наблюдаемое поведение и границы, а не только внутреннее устройство          |

### 6.6. Минимальный набор автопроверок и слепые зоны

| Проверка           | Стартовое правило                                                               |
| ------------------ | ------------------------------------------------------------------------------- |
| TypeScript         | `strict: true`                                                                  |
| Форматирование     | Prettier - единый форматтер                                                     |
| React Hooks        | Правила hooks и зависимости эффектов                                            |
| Неиспользуемый код | Импорты, переменные, экспорты                                                   |
| Размер файлов      | Предупреждение после 350-400 строк (в шаблоне - блокирующий 250 с исключениями) |
| Размер функций     | Предупреждение после 60-80 строк (в шаблоне - сигнал 50)                        |
| Сложность          | Предупреждение >10, порог обязательной проверки 15                              |
| Вложенность        | Предупреждение после 3 уровней (`max-depth`)                                    |
| Параметры          | Предупреждение при >4                                                           |
| Зависимости        | Циклы и запрещённые межслойные импорты                                          |
| CI                 | Проверка типов, lint, тесты, сборка                                             |

Из ограничений размера исключаются: сгенерированные файлы, lock-файлы,
схемы сторонних стандартов, данные, снимки тестов и артефакты сборки;
применённые миграции не дробятся и не исправляются автоматически. Лимиты
размера сначала вводятся как предупреждения; ошибки типов и правила
hooks - блокирующие всегда.

Слепые зоны шаблона (что не покрыто политикой - учитывать в форках и
новых проектах): нет разделения server/client (`console.log` на сервере -
норма, на клиенте - мусор); нет ранжирования ошибок (всё `error` или
`off`, нужен градиент warn -> error через спринт); нет исключений для
сгенерированного кода (`node_modules` игнорируется, `.prisma/` и
`.next/` - нет); нет E2E (только Vitest unit; для UI нужны
Playwright/Cypress на критическом пути); нет правил API-дизайна (REST
naming, HTTP-статусы, формат ошибок не покрыты).

```text
## 4. Anti-Monolith

Hard rule, enforced by a script at pre-commit and in CI:

- A TS/JS file over 250 lines (tests exempt) blocks the commit:
  `node scripts/check-file-length.ts --all`. Generated and vendored paths
  are exempt; each exemption is reported with its reason.

Signals to analyze - guiding checks, not barriers (no auto-stop):

- small UI component (button, card) over 200 lines: almost always mixing jobs;
- behavior component (form, widget) over 250 lines;
- page-level composition over 300 lines: check it does not own data or logic;
- function or hook over 60 lines, or cyclomatic complexity over 15;
- a hook that bundles three or more unrelated jobs.

When a signal fires:

1. State the file's purpose in one sentence without "and". If it fits,
   leave the file as is and continue the task.
2. If it does not fit, split by responsibility: UI separate from data
   fetching, state owned by the nearest parent. Do not create wrappers,
   hooks, or subcomponents to lower a line count.
3. Continue the task normally: the counter is not the goal, cohesion is.

The number of `useState` calls is not evidence by itself: a page with
six `useState` calls can be healthy. Extract a hook for one coherent
behavior with a clear contract; prefer `useReducer` for complex
transitions. A hook that mixes unrelated concerns is the signal.
```

## Приложение Б. Ручные проверки на машине

Семь проверок, которые невозможно выполнить в песочнице. Каждая
занимает одну-две минуты.

1. **Подсветка регулярных выражений.** Открыть `eslint-rules/unicode-policy.js`:
   подсвечиваются ли строки с паттернами как «Неизвестная категория
   символов» в 2026.2.3. Если подсветки нет - ишью починено, обход через
   `String.raw` можно свернуть в литерал.
2. **Save Actions.** Проверить «Настройки -> Инструменты -> Save Actions»:
   активен ли плагин и что он делает при каждом сохранении относительно
   нативных «Действий при сохранении». Ожидание: форматирование плагина
   отключено, иначе - двойное форматирование.
3. **React Buddy.** Сверить список установленных плагинов с
   docs/webstorm.md §9: установлен ли плагин фактически. Ожидание: либо
   доустановка, либо правка §9.
4. **lsp4ij.** Проверить, не даёт ли LSP-клиент дублирующую подсветку
   одной проблемы вместе со встроенными инспекциями. Если дубль
   подтверждается - отключить один из источников.
5. **Переносимость скоупа.** Перенести глобальный профиль инспекций со
   скоупом `generated_changelog` на второй проект: скоуп должен оказаться
   инертным (ссылается на путь этого репозитория). Если влияет - убрать
   скоуп из глобального профиля (глава 3, шаг 4).
6. **Реимпорт rafce после фикса.** После действия 1 из главы 5 -
   реимпортировать `React.xml` из репозитория, создать файл `test.tsx`,
   применить `rafce`: имя `Test` подставилось во все четыре места, `npx
eslint` на файле чистый.
7. **Порядок «Действий при сохранении».** Проверить, что цепочка «ESLint
   fix on save -> Prettier -> Stylelint» не конфликтует: итоговый файл
   проходит `eslint --max-warnings=0` и `format:check` без ручных правок.
