# API: конвенции

Контракты HTTP API для проекта из шаблона. Правила ниже - стартовая точка:
формат ошибок и версионирование важнее конкретного стиля, важно применять их
одинаково во всех ручках.

## Ресурсы и методы

- Путь - существительное во множественном числе: `/users`, `/orders/:id`.
  Действие выражается методом или подресурсом, а не глаголом в пути.
- `GET` не меняет состояние, `PUT` идемпотентен, `POST` создаёт и не требует
  идемпотентности, `PATCH` меняет часть, `DELETE` удаляет.
- Вложенность не глубже двух уровней: `/users/:id/orders` допустимо,
  `/users/:id/orders/:oid/items/:iid` - уже повод пересмотреть ресурс.

## Статусы

| Код | Когда                                                     |
| --- | --------------------------------------------------------- |
| 200 | успешное чтение или изменение с телом ответа              |
| 201 | создан ресурс; в `Location` - адрес нового ресурса        |
| 204 | успех без тела                                            |
| 400 | синтаксическая или семантическая ошибка запроса           |
| 401 | нет или истекла аутентификация                            |
| 403 | аутентификация есть, прав нет                             |
| 404 | ресурс не найден или недоступен пользователю              |
| 409 | конфликт состояния: дубликат, гонка, нарушение инварианта |
| 422 | запрос валиден синтаксически, но не проходит проверку     |
| 429 | превышен лимит; в `Retry-After` - когда повторить         |
| 5xx | ошибка сервера; тело не раскрывает внутренности           |

## Формат ошибки

Одно тело на все ошибки:

```json
{
  "error": {
    "code": "ORDER_NOT_FOUND",
    "message": "Order not found",
    "requestId": "01J8Z6K2Q4",
    "details": [{ "field": "id", "reason": "not found" }]
  }
}
```

`code` - машиночитаемый и стабильный, `message` - короткий и нейтральный,
`details` - опционально для ошибок валидации. HTTP-статус и `code` не должны
противоречить друг другу.

## Валидация и пагинация

- Вход валидируется на границе до бизнес-логики; ошибка валидации - 400/422 с
  перечнем полей.
- Список отдаётся курсором (`cursor`, `limit`), а не номером страницы, если
  данные меняются. Курсор непрозрачен для клиента.
- `limit` ограничен сверху сервером; значения по умолчанию документированы.

## Версионирование и совместимость

- Версия в пути (`/v1/...`) добавляется при первом ломающем изменении, не
  заранее.
- Совместимые изменения: новое необязательное поле, новый эндпоинт, новый код
  ошибки. Ломающие: удаление поля, смена типа, ужесточение валидации.
- Устаревшее поле помечается в документации и удаляется не раньше следующей
  мажорной версии.

## Надёжность

- Таймаут на каждый внешний вызов; повтор только для идемпотентных операций и
  с ограничением числа попыток.
- Идемпотентность `POST` для платежей и подобных операций - через
  `Idempotency-Key`.
- Ошибка внешнего сервиса не превращается в 500 без контекста: клиенту - 502
  или 503, в лог - причина и идентификатор запроса.
